# Nyxus 0.6.0

Released 29 October 2026. Every release and its notes are also at [nyxus.co.uk/releases](https://nyxus.co.uk/releases).

Nyxus 0.6.0 is about standing a deployment up and keeping it honest: nyxusctl install from a key and a cluster or a Docker host, detection sources set up and checked from the console, new AI tools asked about rather than missed, personal sign-ins nobody uses told apart from ones in use, a setup that shows the deployment coming together, one mode instead of two, and a subscription a key cannot run unseen.

## Before you upgrade

A deployment with no licence key stops taking new work three days after this release first starts. Findings, enrolments and discovery candidates are refused from then on; everything already collected stays readable, and the console counts the days down. If yours has never had a key added, add it under System health › Subscription, before or within three days of upgrading.

Classic mode is gone. A deployment installed with managed.enabled=false is refused by this chart with a message that says so, rather than upgraded into a database it chose not to have. Stay on 0.5.0, or move to Shadow AI Guard, which keeps that mode. Every other deployment upgrades as before; the leftover settings from having two modes are ignored, and what helm prints after the upgrade lists any it found.

Redeploy the collectors after upgrading. Collector 2.3.0 sends when a signed-in tool was last used and asks about AI tools nobody has added; until a machine runs it, its sign-ins are treated as in use, as before, and nothing it would have asked about is asked. Download each platform's collector again from System health › Collector downloads and push it the way you pushed the last one.

## Security

The receiver, discovery and scanner images carried a certifi bundle with emSign root certificates whose intermediate keys were compromised (GHSA-6q48-6c7w-9gw2, critical). certifi is updated in all three.

The portal image carried dnspython 2.8.0, which a crafted DNS answer could tie up in compressed names (CVE-2026-114605, high). It is updated to 2.9.0.

The answer the registry signs is now proved again every time it is consulted, not only when it arrives. Until this release it was reduced to the word "active" and a timestamp in a table on a writable volume, and one change to that table outranked the signature.

A key runs one deployment at a time, as it has since 0.2.0. Three ways round that are closed: a grace clock moved forward by hand, an answer deleted from the table, and a subscription feed setting that carried its own query and asked the registry without naming the deployment. Each now degrades over the normal fortnight rather than running for ever. A key in use elsewhere, or one the registry does not recognise, is measured from the last time this deployment was confirmed active, and no longer from the last answer it got.

Security reports go to support@nyxus.co.uk with "security" in the subject. The security model is published at nyxus.co.uk/kb-articles/security.

## Standing a deployment up

```
nyxusctl install --kubernetes
nyxusctl install --compose --directory ./nyxus
```
From a licence key and a cluster: the namespace, the pull secret and the release, then what to do next. From a key and a Docker host: the compose file, the compiled tool registry, the secrets and the stack. It prints the plan before it runs anything, and --dry-run needs no key at all. The key travels only in a file only you can read, removed when it is done.

On a machine that could do either, it asks you to choose rather than choosing. It asks nothing else unless you pass -a: an ingress pointed at a name that does not resolve looks installed and cannot be reached.

## One mode

Nyxus runs one way: accounts, enrolment, central settings and the fleet inventory, backed by a small database on a volume. The basic-auth portal and its settings are removed. Set PORTAL_USER or PORTAL_PASSWORD and the portal will not start, and say why; it signs in with the receiver's accounts.

## Identities that are not people

A build agent or a shared mailbox is not a person, and was counted as one: in "affected people", the people count on the AI register and evidence pack, team coverage gaps, the digest, Budget's seats and a tool's People list. Mark one Not a person on People and it is counted as none of those, everywhere. Recorded snapshots keep the count they were taken with.

A device somebody has already mapped to a person is no longer offered as one to map, whether it was mapped by its key, a serial or a local username.

## Detection sources, set up from the console

Entra (with Intune and Exchange), Jamf, SentinelOne, NinjaOne, Datto RMM and discovery can be set up under Detection sources › Set up sources, step by step in each product's own screens, instead of in a Secret. Credentials are sealed in your browser to a key only the scanner and discovery hold, so the receiver stores what it cannot open, and they are never shown again. Only an owner can save them, confirming their password or a recent single sign-on, and the other owners are emailed which source changed and who changed it, where mail is set up.

Each connection is tested before it is saved - signed in, and which of the permissions it needs it has - and can be checked again at any time. Detection sources leads with what needs attention: a failing connection, a client secret within 30 days of expiring, sources not set up, collectors older than the current version. A source you do not use can be marked so, and is left out of coverage.

A credential in a cluster Secret still wins for its source, so nothing changes until you move one. The chart makes the scanner's key and a token that proves a request comes from this deployment's scanner rather than a laptop claiming to be one, and runs a small check process beside the receiver while the scanner or discovery is on; sourceCredentials.enabled=false turns all of it off. Under Compose, nyxusctl install writes all of it into a new stack, and nyxusctl upgrade adds it to one from before 0.6.0 as docker-compose.sources.yml beside your own file, which it does not edit, named in COMPOSE_FILE in .env so a later docker compose up keeps it.

NinjaOne and Datto RMM are new sources: the software each RMM already inventories, read-only.

## New AI tools, asked about

The collectors, and the Intune, Jamf, NinjaOne and Datto RMM inventories, now ask about AI-looking apps, browser and editor extensions and commands that the registry does not know, rather than passing over them. They arrive under Discovery › Unrecognised observations with how many devices they are on, once a day per machine, and become detections only when somebody adds them to the registry. What looks like AI - the words and fragments that make a name worth asking about - is changed under Administration › Detection & paste guard › Looks like AI.

A tool added from that queue is detected where it was found, including Windows programs listed by their installer name and commands found on PATH. A tool's registry entry can say where it keeps its signed-in account, and editing it no longer drops the fields the form does not show.

## Sign-ins nobody uses

A personal account found in a file on a machine was reported as in use today, because the collector saw it today. Collector 2.3.0 sends when the tool was last used instead. A sign-in unused for longer than Administration › Display & alerting › Dormant after (7 days unless you change it) is listed on Personal accounts as signed in but not used, and is not counted, alerted or paged. A machine that has not sent a last-used time is treated as in use, so nothing drops out on upgrade day.

Every time in the console is shown in one time zone, Europe/London unless you choose another, with GMT and BST said as the clocks change.

## A budget summary for finance

On a day of the month you choose, Budget › Monthly summary emails what the AI tools cost - the total, then each tool's plans, licences and monthly cost, with the same figures as CSV - to recipients of its own. It names nobody: no members, owners or roles. It goes through the company's own mail server, so outbound mail must be set up first.

## Setup, the move and Settings

Setup is nine steps in three parts - start collecting, make it useful, roll out - with the deployment drawn above every step and lit from what is actually in place, and a test beside each thing it asks for. An owner or admin's first sign-in opens it on a new deployment, and opens the guide to the move on one moved from Shadow AI Guard. Pages it sends you to offer the way back.

Settings is a list of sections, each a panel of tabs, with a search across every setting and one bar to save a page. Alertmanager can be sent a test alert from Display & alerting › Warnings, which clears itself after five minutes.

## When collection has stopped

Every surface now says so in words. The subscription card names the state - in use elsewhere, not recognised, unconfirmed, withdrawn - and is green only when the registry has confirmed it. Two weeks without a confirmation says that new work has stopped and which host to open, not "contact Nyxus", because it is almost always the egress. The scanner and discovery stop at the first refusal and log the reason once, rather than a bare 402 for every finding; discovery checks before it spends anything on classification.

## Also in this release

- System health lists the upgrades nyxusctl is waiting on you to approve. The only way to find one was the code in the terminal, and a link carrying a query string opened an empty page.
- Budget with nothing set up shows the one thing to do, and claims nothing the read did not support.
- The top bar stays on one line in a narrow window.
- The chart's README - what helm show readme prints - installs into the namespace it just made, with the pull secret, and its upgrade examples keep the values you set. The example NetworkPolicy lets the portal and the CronJobs reach the receiver.
- In the dark theme, three colours used across ten pages drew nothing. They are back.
- A decision's rationale was saved and never shown; it is now on the register and in its export. Revising an approval that had lapsed no longer records "approval_expired" as its rationale.
- A report or invitation sent through a slow mail server no longer shows as failed while it is still being sent.
- Figures that disagreed from page to page now agree: lapsed approvals, devices without a collector, agent runs nobody owns, paste catches, and a rule's preview against the rule once saved.
- A team viewer who opens a page by its address that is not theirs is told so, rather than shown it drawn on refused reads.
- A log store or Grafana configured in the portal's environment shows as set by the deployment, not "Not set".

## Getting nyxusctl

nyxusctl upgrade needs 0.6.0's nyxusctl: 0.5.0's re-pulled the same image on Compose and reported success. An older one stops and prints the command to get this one.

```
curl -fL -u licence:$NYXUS_KEY \
  https://registry.nyxus.co.uk/cli/0.6.0 -o nyxusctl-0.6.0-py3-none-any.whl
pipx install --force ./nyxusctl-0.6.0-py3-none-any.whl
nyxusctl --version
```
Keep the file's full name: pip reads the project and version from it. 0.5.0's notes saved it as nyxusctl.whl, which pip refuses, and the registry named it wrongly too; both are fixed. nyxusctl self-update --version 0.6.0 does the same download.

## Upgrading

```
helm upgrade nyxus oci://registry.nyxus.co.uk/nyxus-enterprise/charts/nyxus \
  --version 0.6.0 -n <namespace> --reset-then-reuse-values --wait
```
or nyxusctl upgrade, which passes the right flag itself and works for Compose too. On Compose it also adds what detection sources set up in the console need, as above, and shows it in the plan before anything runs.

- Check what you are running rather than trusting the success message: the receiver answers its version at /healthz, and System health names it.
- Collector CronJobs you maintain by hand stay outside the chart until adopted: run nyxusctl move, or set their tags as before. Sources set up from the console need the chart's scanner and discovery, which mount the scanner's key; CronJobs kept by hand go on reading their own Secrets.
- Redeploy the collectors at 2.3.0, as above.
- Every image and the chart are signed and verify against the key introduced in 0.2.0. That key and the commands to check a signature are in the chart's README:

```
helm show readme oci://registry.nyxus.co.uk/nyxus-enterprise/charts/nyxus --version 0.6.0
```
The receiver adds tables for identity kinds, source credentials and their checks, and the finance summary's schedule and runs, and records when it first ran, all on start. No migration step. Collector 2.3.0 adds when a tool was last used to what it sends, and the names of unknown AI-looking tools; nothing else that is collected changes.
